## 0. 先读：B组必须遵守的产品定位

OneBoss 是 AI 创意宣传制作公司。**客户是找OneBoss付费制作宣传素材的商家、厂家、品牌方或个人**；其产品可以是椅子、汽车、饮料、衣服、数码商品、摄影服务等合法商品/服务。客户购买的是宣传制作服务：网站链接、静态海报、二维码、小红书文案和完整交付包。

客户在OneBoss官网选择套餐、创建订单、完成可信支付确认后（或有清晰沙箱标识的演示），提供有限产品资料，经MiMo智能反问、AI创意总监选择风格，进入创意生产。**OneBoss不替客户做广告投放、成交、库存、物流、商品支付，也不做3D建模。**

B组的P0作品：

- **真实交互式宣传网站**：需要网站的实际 React 渲染器，而非一张长图、静态设计稿或模型生成的HTML字符串；在手机上有可操作的轮播/选项卡/详情/导航等；交由A组公开部署URL。
- **真实高清PNG海报**：由 B组的渲染器根据产品事实、真实素材、AI设计规范输出可下载PNG，而非仅显示示意图；包含二维码，默认放**右下角**，当右侧冲突才放**左下角**。
- **小红书配套文案**：每张海报和其标题、正文、标签、引导语统一存成 `PosterCopyBundle`；由同一事实版本产生，前端可以复制与下载；OneBoss本身不自动发表。
- **AI创意总监**：依据客户提供的产品提供2–3套真正有布局/色彩/图文节奏差异的设计方案，并根据自然语言**局部修改**而非每次全量重制。

B组负责设计与渲染，A组负责支付、数据、授权、MiMo网关、文件存储和正式发布。**两组不能各写一套订单系统、MiMo客户端、网站schema。**

## 2. GitHub 开源项目借鉴策划（B组专用）

### 2.1 B组的最小推荐组合（先做这五个）

1. **shadcn/ui**：优先解决OneBoss官网和工作台的专业质感。
2. **Motion**：把交互式网站和静态海报明显区别开，使用克制动效。
3. **Satori**：使用受控模板真正输出SVG海报。
4. **Sharp**：对商品图片处理，并输出高清PNG。
5. **QR Code Styling**：海报右下/左下可扫码的二维码。

**Puck不是第一个要安装的项目。**先实现受控的 `SiteSpec` + React渲染，等 P0 稳定后再引入Puck编辑已有结构；否则容易出现“编辑器能拖动，但模型生成内容根本无法渲染”的问题。Design Editor同样只在时间允许时引入。

### 2.2 开源资产审核文件

Codex必须在 `docs/opensource-audit-b.md` 保存：项目名、用途、研究模块、依赖版本、许可证、引入方式、引入成本、是否加入正式版本、回退方案。**任何开源项目的许可证和第三方依赖许可证以正式安装时核对的仓库内容为准。**

## 3. 网站必须为什么不等同于海报？最终交互标准

网站提供**探索产品**的交互体验；海报提供**直接传播**的静态画面。二者共用设计规范，但具有不同的内容组织和渲染机制。

### 3.1 站点形态（同一引擎支持三种）

| 站点类型 | 适用客户 | 首版页面结构 |
|---|---|---|
| 单品着陆页 | 一款椅子/一款汽车新品 | 产品主视觉、图库、卖点、参数/详细说明、联系入口 |
| 多产品展示站 | 家具店有5款椅子 | 品牌首页、商品卡片列表、商品详情、品牌简介 |
| 品牌介绍站 | 企业、工作室、品牌 | 首页、品牌故事、产品系列、案例/图库、联系方式 |

注意：客户输入一种产品时不应强迫生成“单页长图”。有足够产品资料时自动生成多页面导航；资料不足时可以以单品互动页交付，客户之后新增产品时扩展，不需要重新建站。

### 3.2 必须真实实现的交互组件

| 组件ID（建议） | 最低行为 | 风格可调整 | 失败兜底 |
|---|---|---|---|
| `hero` | 大图、标题、副标题、按钮锚点 | 主视觉构图/对齐/字体 | 图片缺失则使用文字布局 |
| `gallery` | 点击/滑动切图、指示点、缩略图 | 网格或轮播 | 仅1图时不显示不可点击控制 |
| `featureCards` | 展开或卡片动效展示卖点 | 卡片排列与颜色 | 降级为静态卡片 |
| `specTabs` | 切换规格/参数面板 | tabs或accordion | 无规格则隐藏模块 |
| `productGrid` | 点击产品卡进入详情 | 网格列数/卡片比例 | 只有1产品时可隐藏目录 |
| `brandStory` | 文图交替、详情展开 | 图片比例/段落节奏 | 无故事时不编造 |
| `stickyNav` | 锚点跳转并标记所在区块 | 透明/纯色/置顶 | 小屏可折叠菜单 |
| `cta` | “了解更多/联系品牌”跳转经确认的地址 | 按钮形状/视觉层级 | 无确认链接则不展示按钮 |
| `scrollReveal` | 在进入视口时做轻度动效 | 动画强度/时长 | `prefers-reduced-motion`直接展示 |

**P0至少完成**：hero、gallery、featureCards、specTabs/accordion、nav、CTA、移动端适配；动画只用于增强体验，不得让页面变得卡顿或依赖高性能设备。

### 3.3 三类视觉方案必须真正不同

**A：精致极简**——大面积留白、清爽字阶、少量主色、轻度动效、产品摄影主导、模块间距大；适合家具/高端生活方式。

**B：未来科技**——深色背景、清晰的信息卡、科技细节/线条、局部冷色强调、参数模块更突出；适合数码/汽车科技主题。

**C：年轻活力**——鲜明配色、大标题、不对称卡片、节奏更快的动画、社交媒体视觉；适合潮流/消费品。

**不得只有配色不同**：对同一商品至少有两套候选方案在Hero构图、图文比例、章节顺序、字体层级、卡片类型或动效预设方面出现明确差异。禁止把AI产生的通用宣传语包装成经确认的产品事实。

### 3.4 响应式和可访问性要求

- PC宽屏、平板、手机窄屏均可浏览；至少测试375px、768px、1280px视口。
- 移动端产品轮播可触摸操作，滑动不会导致整页横向溢出。
- 图片含替代文字，主要交互可键盘操作；按钮有可见focus状态。
- 低性能设备或低速网络优先显示内容，不让动画阻挡阅读。
- 对减少动画偏好的用户尊重 `prefers-reduced-motion`。
- SEO标题和描述只使用已确认产品名称、介绍，不编造“第一”“最安全”等未核实卖点。

## 4. 高质量海报渲染器：从设计配置到真PNG

### 4.1 固定画布与导出规范

| 输出 | 尺寸（首版） | 格式 | 要求 |
|---|---:|---|---|
| 小红书竖版主海报 | 1080 × 1350 | PNG | 核心卖点、真实商品图、QR、引导语 |
| 方形宣传图 | 1080 × 1080 | PNG | 同风格但重新排版，不靠直接裁切竖版 |
| 二维码独立文件 | 按需求（建议≥300像素） | PNG/SVG | 高对比度、保留quiet zone |
| 海报编辑配置 | 原画布大小 | JSON `PosterSpec` | 支持更新文本、图片与颜色后重新导出 |
| 小红书配文 | 不限 | TXT/Markdown | 标题、正文、标签、发布时间提示（不代表自动发帖） |

### 4.2 海报版式安全规则

1. 二维码默认**右下**，右下与商品主体/价格冲突时**左下**，仍冲突则提示设计师选择合适布局，不擅自盖住重要内容。
2. 二维码周围必须有完整的浅色安全底与静区（quiet zone），不能随意放在杂色背景中。二维码实际尺寸及最小模块尺寸要以扫码测试为准；建议在1080px画布中预留大约150–200px宽的安全区域，最终以测试调整。
3. 文案、价格、Logo、联系方式与二维码不可相互覆盖；超出区域时优先简化文案、增大留白、改变布局，不允许强行缩小到不可读。
4. 优先使用客户拥有权利的实拍产品图。无素材时允许图文/几何图形海报；不可伪造汽车参数、椅子材质或生成未确认的真实商品形象。
5. 价格与参数从 `ProductFact` 引用，不能让海报Agent自行改价；如果客户不愿展示价格，海报不得补上AI猜测金额。
6. 中英文/数字/货币符号排版完整，图片、字体及中文文字在**最终PNG**检查，不能只看浏览器CSS预览。
7. 导出后读取图片尺寸、颜色通道、背景和有效像素，避免空文件、透明空图、零字节文件。

### 4.3 PosterSpec 推荐结构（数据合同，非开源源码）

```json
{
  "schemaVersion": "1.0",
  "projectId": "demo-chair-001",
  "revision": 1,
  "canvas": { "width": 1080, "height": 1350 },
  "designSystemVersion": 2,
  "layout": "editorial-premium",
  "layers": [
    { "type": "background", "ref": "palette.background" },
    { "type": "image", "assetRef": "real-photo-front", "fit": "contain" },
    { "type": "text", "factRef": "product.name", "role": "headline" },
    { "type": "text", "factRef": "product.price.display", "role": "price" }
  ],
  "qr": { "placement": "bottom-right", "urlSource": "published-site", "caption": "扫码查看详情" },
  "copyPackRef": "copy-pack-001",
  "factVersion": 1
}
```

**这里的 `qr.urlSource=published-site` 是流程占位符，正式PNG渲染前必须由A组传入已验证的真实URL。**

### 4.4 Satori + Sharp的实施边界

- Satori生成SVG，适合确定性模板、统一字体与规范化排版；**不等于完整浏览器CSS渲染**，Flex等布局要在真实渲染中验证。
- Sharp可把SVG转PNG、裁切图片、合成QR模块；必须有服务端可用的运行环境。
- 中文字体需在构建/运行时提供合规授权的字体资源并正确加载；**不要把需要许可的字体私自打包公开分发**。
- 如果Satori中文布局问题影响T18关键节点，立即回退到可控的 SVG模板+Sharp，不能一直调大编辑器。
- 需要保存海报编辑原始配置，重新生成同一布局时无需再调用AI从零重做。

## 5. 每张海报绑定一套小红书文案

### 5.1 文案包约束

- 标题：与海报主要创意和产品一致；不伪造体验、成交、口碑或使用评价。
- 正文：产品是什么、适合什么场景、已确认的亮点、温和的了解更多引导；不能宣称从未提供的材质/性能。
- 标签：与商品类型相关、不堆砌无依据的热点标签。
- 封面字建议：可与海报主标题一致或互补，但不引用未经确认的绝对化卖点。
- 引导语：可说明“扫码了解更多”，但实际外部平台对二维码/导流可能有限制，**OneBoss只提供素材与适配副本，不自动发表，也不保证平台审核通过**。
- 同一 `factVersion` 贯穿网站、海报、小红书配文；客户改价后需重查所有使用该价格的文案。

### 5.2 文件输出

`copy/xiaohongshu-poster-01.md` 至少包含标题、正文、标签、海报文件名、关联网址、事实版本、制作时间。B组前端提供一键复制和下载，A组最终打入ZIP。

## 6. AI创意总监：专业设计职位，而非换色按钮

### 6.1 五个关键工作阶段

| 阶段 | 输入 | 输出 | 客户可参与的动作 |
|---|---|---|---|
| 理解产品 | 已确认产品事实、图片、品牌/目标、参考风格 | `CreativeDirectionBrief` | 补充必要资料 |
| 生成候选 | 商品和设计限制 | 2–3套 `DesignSystem`候选与差异说明 | 选择候选或提出修改 |
| 统一指导 | 被选中设计方案 | 对网站/海报/文案的风格指令 | 确认项目风格 |
| 审核作品 | 网站预览、海报预览、文案包 | `CreativeReview`：需修的问题 | 接受/要求返工 |
| 理解修改 | 客户自然语言、当前版本 | `ChangeRequest`指定受影响作品 | 修改范围确认与最终批准 |

### 6.2 高质量创意总监必须提供的选择

以“家用椅子 129元”举例，至少给出：

- 极简家居方向：大量留白、真实椅子高清大图、居家氛围、大段距离、温和色系。
- 年轻生活方式方向：强对比色、生活场景插图/真实照片、动态产品卡、强调设计与价位。
- 如果仅一张图片，不得凭空承诺提供真实的背面、其他颜色或多角度图；可以使用同一真实图片做裁切布局。

以“18.98万元的汽车”举例，除非客户明确授权并提供可核实的车型参数，创意总监只能基于“汽车/品牌/已知价格”设计高品质视觉，不得虚构续航、碰撞成绩、辅助驾驶能力、限时促销等。

### 6.3 修改意图解析规则

- “网站改黑金，海报不动” → `targetArtifacts=[site]`，只做网站颜色/排版变更。
- “价格从129改139” → 标记 `isFactChange=true`，要求事实审核，触发网站+海报+文案影响检查。
- “标题更高级些” → 文案改写，保留已确认商品事实，重新检查相关作品。
- “换一张主图” → 从客户已授权的素材中选；若无图则询问用户上传，不擅自调用外部不明素材。
- “把所有内容都改成极简风” → 需要网站+海报统一更新设计规范版本。
- “只把海报二维码换到左下角” → 只改海报二维码 placement，不能让网站重新构建。

每次修改产生可解释的差异清单，用户可批准或撤销。审核之前不覆盖已发布版本。

## 8. 与A组共同使用的数据合同（必须与A组文档一致）

### 8.1 共享真实数据源

**商品事实**：A组负责 `ProductFacts`，B不可另存自己的商品价格真相。  
**品牌风格**：B主导 `DesignSystem`，A保存并版本化。  
**网站设计**：B生成 `SiteSpec`，A审核授权并发布。  
**海报设计**：B生成 `PosterSpec`、渲染真正图片，A存储并核验。  
**客户修改**：B提供意图解析逻辑/UI，A保存 `ChangeRequest`/审批/版本。  
**交付包**：A建立 `DeliveryManifest`，B负责展示和用户操作。

### 8.2 具体契约列表

| DTO | B必须生成或消费 | 不能违反的规则 |
|---|---|---|
| `CreativeBrief` | 消费 | 客户未确认价格不能当已确认事实 |
| `ProductFact` | 只读消费/提出变更请求 | 价格字段来源于A事实库，不在编辑器直接篡改 |
| `DesignSystem` | 主导生成 | `palette/typography/layout/motion`字段由双方Zod统一 |
| `SiteSpec` | 主导生成和渲染 | 只使用已实现组件和交互枚举；不允许任意JS |
| `PosterSpec` | 主导生成和渲染 | 受控图层、QR角落、安全距离和已验证URL |
| `PosterCopyBundle` | 主导生成 | 每张海报对应标题、正文、标签、factVersion |
| `ChangeRequest` | 提交编辑操作 | 指定目标作品、baseRevision、是否事实修改 |
| `DeliveryManifest` | 消费并展示 | 不自行伪造“已交付”或文件链接 |

**函数交接**：B实现 `renderSite(spec, designSystem, productFacts, assets) -> ReactUI` 和 `renderPoster(spec, resolvedQr) -> pngBytes/svgBytes`；A负责公开路由、文件存储与交付ZIP。B不直接写 `payment_attempts` 或 `service_orders.pay_state`。

### 8.3 用来独立开发的固定fixtures

至少准备以下样例，在合同仓库里统一管理：

1. **椅子零售**：原木家用椅，129元/把，1张有授权的实拍，缺少材质/尺寸时不写虚假参数；站点需要轮播/特点介绍。
2. **汽车宣传**：示例汽车，指导价18.98万元，无未核实续航参数；科技视觉、图库、品牌介绍。
3. **无图产品**：仅名称+价格+一句介绍，要求图文型网站和海报兜底，不生成假实拍。
4. **多个产品**：同品牌3款家具，共用品牌风格但独立产品详情。
5. **修改**：“网页改黑金、海报不变”和“129元改139元”两种，验证目标范围和事实审批区别。

这些fixture是开发测试样例，不可充当正式客户订单和真实AI运行记录。

## 12. 详细验收矩阵（B组自己必须做完）

### 官网与套餐

- [ ] 官网像一家真正出售创意制作服务的公司：能看案例、了解服务、选择套餐、创建订单。

- [ ] 主要流程手机上都能完成，包括上传、反问、确认创意、预览、下载。

### 创意总监

- [ ] 同一把椅子至少两套方案**布局/层级/动效等确有差异**，不只是换色。
- [ ] 不同商品如汽车、家具有相应设计节奏，且未知参数保持“待确认”。
- [ ] 客户说“网站改黑金，海报不变”，只针对网站生成新版。
- [ ] 无商品照片时仍能生成专业图文宣传设计，不能伪造商品实拍。

### 网站

- [ ] 有真正React交互（图片轮播、选项卡/展开、导航），不是页面截图。
- [ ] 产品1张图时不显示无法操作的“下一张”按钮；多张图时轮播正常。
- [ ] 375px、768px、1280px无严重排版错乱、溢出或遮挡。
- [ ] 客户拥有10款产品时能生成产品列表和详情，而不只是每款一个无关联网页。
- [ ] 任何网页链接、品牌联系方式必须来自已确认的来源，不随便乱填。

### 海报和二维码

- [ ] 1080×1350和1080×1080各生成一份独立布局的真实PNG。
- [ ] 无中文乱码、主图错位、字体过小、价格遮挡、空白图。
- [ ] QR在右下角或必要时左下角，不遮挡产品主体、保留足够安全区。
- [ ] 真实公开链接由A发布验证后注入，手机实际扫码成功。
- [ ] 小红书文案与每张海报一一对应；标题/正文/标签可复制及下载。
- [ ] 商品事实变化后，文案和海报能够重新生成或标记待更新，旧版不被静默覆盖。

### 与A集成

- [ ] `SiteSpec`和`PosterSpec`来自共同Zod Schema，不能在B组私自加破坏字段。
- [ ] B不读取支付密钥、MiMo Key或其他租户私有文件。
- [ ] A可以无UI直接调用B渲染模块得到网站和PNG，不依赖B的页面点击顺序。
- [ ] 失败时提供真实错误反馈，不把测试fixture标为真实客户交付。

## 15. 风险处理、降级和禁止事项

| 风险 | 可落地降级 | 什么绝不能假装已完成 |
|---|---|---|

| MiMo输出设计越界 | Zod拒绝+调用合法模板重新生成 | 执行任意AI脚本或让B自己编造事实 |

| 支付接口未通过 | 明确模拟/人工核验下单 | 前端点“付款成功”当真实付款 |
| AI随意重做 | 精准变更指定站点/海报+预览 | 覆盖客户原已批准作品 |

**B组必须坚持：简化功能可以，双核心交付的真实性不能降级。**
