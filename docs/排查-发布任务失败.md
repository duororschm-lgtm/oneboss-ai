## 三、为什么错误码是 `TASK_FAILED`

`src/lib/workflows/runner.ts` 第 195–201 行：

```ts
} catch (error) {
  const code =
    error instanceof AppError
      ? error.code                    // 业务规则错误，带具体码
      : error instanceof z.ZodError
        ? 'SCHEMA_INVALID'            // 模型输出不合 schema
        : 'TASK_FAILED';              // ← 其余全部归到这里
```

`TASK_FAILED` 的字面含义是：**抛出了一个既不是业务断言、也不是数据校验的底层异常**。

所以可以排除：
- ❌ 不是"没批准就发布"（那会是 `APPROVAL_REQUIRED`）
- ❌ 不是"版本过期"（`STALE_REVISION`）
- ❌ 不是"模型输出不合规"（`SCHEMA_INVALID`）

剩下的是基础设施层面的崩溃：浏览器起不来、请求超时、进程被杀。

## 四、publish 这一步到底做什么

入口 `src/lib/publishing/service.ts:66 publishRevision()`：

```
1. 先把项目标记为已发布（乐观写入，失败会回滚）
2. verifyPublicUrl()            —— 用 HTTP 抓公开页，确认 HTML 里有当前版本标记
3. verifyPublishedBrowser()     —— 启动 Chromium 做三宽度验收   ← 最重的一环
4. 通过后写 published_verified=true，状态改 PUBLISHED
5. 任一步失败 → 回滚 published_revision，抛出原异常
```

### 浏览器验收的具体动作

`src/lib/publishing/browser.ts`：

```ts
const browser = await chromium.launch({
  executablePath: process.env.BROWSER_EXECUTABLE_PATH,   // 容器内 /usr/bin/chromium
  args: ['--disable-dev-shm-usage', '--disable-gpu', '--renderer-process-limit=1'],
  timeout: 30000,
});

for (const width of [375, 768, 1280]) {
  await page.setViewportSize({ width, height: 900 });
  await page.goto(url, { waitUntil: 'networkidle', timeout: 30000 });   // ← 可能超时
  // 检查：版本标记 / 无横向溢出 / 图片全部加载
  await page.locator('[data-oneboss-interaction]').first().click({ timeout: 10000 });  // ← 可能超时
  await page.waitForFunction(/* DOM 必须变化 */, before, { timeout: 5000 });           // ← 可能超时
}
```

任何一个 `timeout` 触发，抛出的都是 playwright 的 `TimeoutError` —— 这是**裸异常**，不是 `AppError`，所以最终被记成 `TASK_FAILED`。

## 五、三种可能原因（按可能性排序）

### ① 512MB 内存不足，Chromium 被 OOM 杀掉（最可能）

依据：`未完成事项.md` 的 A-01 记录里写着 —

> Render 历史事件确认曾因**超过 512MB** 重启

当前部署是 **Free 档：0.1 CPU / 512 MB**，而一个容器里同时跑着：Next.js 服务 + 后台 worker + Chromium。Chromium 单进程通常要 200–300MB，三宽度连续加载三次，很容易触顶。

### ② 页面加载或交互检查超时

`networkidle` 要等 500ms 内无网络活动，页面里如果引用了 Supabase Storage 的签名图片，或者有轮询请求，30 秒上限可能不够。交互检查只给 5 秒，客户站如果 JS 较重也会超。

### ③ 容器里的 Chromium 起不来

Dockerfile 里装的是 `chromium` 包并设置了 `BROWSER_EXECUTABLE_PATH=/usr/bin/chromium`。如果 slim 镜像缺依赖库，`chromium.launch()` 会直接抛错。

## 六、怎么定罪（需要看 Render 日志，约 1 分钟）

Render → 服务 `oneboss-core` → **Logs**，搜索以下关键词：

| 搜索词 | 命中说明 | 对应结论 |
| --- | --- | --- |
| `Exit status 137` 或 `Killed` | 进程被系统杀掉 | **内存不足 → 必须升 2GB** |
| `TimeoutError` | playwright 超时 | 页面加载/交互问题 → 代码可优化 |
| `browserType.launch` 或 `Failed to launch` | 浏览器启动失败 | 镜像缺依赖 → 改 Dockerfile |
| `Target closed` / `Protocol error` | 浏览器中途崩溃 | 也可能是 OOM |

同时打开 Render 的 **Metrics** 看事件发生时间点（16:35–17:07 UTC）的内存曲线 —— 如果内存顶到 512MB 然后掉下来，基本就是 OOM。

## 七、两个修复方向

### 短期：把错误码细化（我可以直接做）

当前三种完全不同的原因被压成同一个 `TASK_FAILED`，导致**根本没法定位**。建议改成：

```
BROWSER_LAUNCH_FAILED        浏览器起不来
BROWSER_NAV_TIMEOUT          三宽度加载超时
BROWSER_INTERACTION_TIMEOUT  交互检查超时
BROWSER_CRASHED              进程被杀 / 连接断开
```

改动点在 `src/lib/publishing/browser.ts`：把 `chromium.launch()`、`page.goto()`、`click()`、`waitForFunction()` 分别包 try/catch，转成具体 `AppError`。这样下次失败，错误码直接告诉你答案。

### 长期：内存决策

| 档位 | 内存 | 价格 | 能否解决 |
| --- | --- | --- | --- |
| Free | 512 MB | $0 | ❌ |
| Starter | 512 MB | $7/月 | ❌ 内存没变，白花钱 |
| Standard | **2 GB** | $25/月 | ✅ 大概率解决 |

如果日志确认是 137/Killed，免费档和 $7 档都救不了，只能上 2GB。

## 八、复现方式

1. 客户在「作品预览」里批准并发布 → 会重新触发 `publish`
2. 或者直接对同一项目重跑发布任务
3. 观察 `agent_runs` 里 `role='publish'` 的最新记录和 Render 日志

⚠️ 在原因确认前，反复重试只会重复消耗浏览器进程，不会自愈。
